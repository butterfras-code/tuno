The foundation is worth keeping.

Strict TypeScript, an immutable rhythm score, separate practice engines, and extensive tests give this project useful boundaries. I found no reason in this audit to replace the framework or rewrite the music model.

The first fixes are specific.

A stale tab can overwrite student data. The release command omits current rhythm checks, and one omitted check is broken. Those are more urgent than reorganizing large files.

01
FirstReproduced defect

A second tab can erase saved student data.

Each tuNotes tab reads one snapshot at startup, then replaces the entire storage value on every save. There is no revision check or coordination between writers. A harmless settings change in an older tab can remove a profile created in another tab, while both stores still report that storage is working.

Reproduced with two NotesStore instances sharing one adapter
  1. Open A and B against empty storage.
  2. Create Alice in A. Storage now contains Alice.
  3. Toggle showKeySignature in B.
  4. Storage now contains profiles: []. A still shows Alice in memory.

Fix: establish a single-writer or transactional persistence policy. Detect stale sessions and preserve their unsaved work for export. A storage-event listener alone is not an atomic write guarantee; concurrent writes and deletion need explicit handling.

Acceptance: exercise two real tabs, overlapping saves, import, and clear. A stale tab must neither remove newer records nor resurrect deleted ones.

02
FirstConfirmed coverage gap + failing check

The release command misses newer rhythm checks.

verify.mjs maintains its own hard-coded list, separate from package.json. Thirteen of the 42 files named *browser-check.mjs are not named in that list. Some may be historical, so this count is an inventory gap—not thirteen missing features.

Current workflows are among the omissions: counting corrections, responsive performance, UIL presets, and the preset picker. The counting runner includes other scenarios, but does not pull in those checks.

An omitted check has already drifted
node scripts/rhythm-uil-browser-check.mjs
TypeError: Cannot read properties of null
(reading 'options')

The scenario expects [data-setting="teaching-preset"] to be a select. The current UI uses a preset trigger and dialog. This is a broken test contract; it does not establish a broken UIL feature.

Fix: use one explicit check registry with engine support and active/retired status. Generate both browser and release runs from it. Repair the UIL scenario using the current user flow; audit the other omissions before enabling them.

Acceptance: adding an unclassified browser check fails validation. A release run includes current counting corrections, preset selection, and completed performance workflows in both supported engines.

03
NextMeasured stress case

Every saved answer processes the whole history.

observe() calls update() on the answer path. That clones the complete snapshot, validates every profile and record, serializes it, and measures its byte length. Only the final write is deferred. Feedback and advancing to the next note happen after this work returns.

57.2 msmedian synchronous update
7 calls · 50.4–62.2 ms

Valid 3,765,148-byte fixture: 16 profiles × 20 preset contexts, up to 8 pitches per context and 10 observations per pitch. Node 24.22.1 on this host; storage writes were a no-op. This is a synthetic history-load measurement, not a Chromebook or browser timing claim.

Fix: validate full snapshots at import/load boundaries; use narrow, validated updates during play. Avoid cloning unrelated profiles and serializing the whole history just to decide whether pruning is needed. Preserve export limits and failed-write behavior.

Acceptance: benchmark small and near-limit histories on a target school device. Adding unrelated profiles should not materially delay answer feedback.

04
NextMaintenance risk · no defect claimed

Rhythm screen transitions need one owner.

The musical domain has a clear source model. Screen state is less explicit: responsePanel, responseOptionsOpen, feedbackOpen, and performing are mutable variables in the entry module. Handlers must remember cancellation, editor suspension, persistence, focus, and rendering in the right order.

updateResponseView() also sets visibility, input inertness, SVG roles and labels, workspace behavior, and performance annotations. A future panel change has a broad regression surface, especially for keyboard and assistive-technology behavior.

A useful extraction boundary
event: OPEN_FEEDBACK
state: { panel: "feedback", performing: false }
effects: cancel capture, suspend editor, focus feedback

Illustrative contract—not a proposed replacement music model.

Fix: extract typed screen transitions and their effects, then render from that state. Keep the score, answer, and assessment models intact. The 602-line multiplayer view is another future candidate, but file length alone does not justify splitting it.

Acceptance: table-test transitions during capture and review; retain browser checks for focus, interrupted attempts, and checked answers across panel changes.

05
NextMaintenance risk · no defect claimed

Persisted practice identity is an untyped tuple.

The fingerprint is both a comparison key and a data format. Its writer builds an unknown[]; persistence reparses it and reads fields such as parts[5], parts[6], and parts[7]. Validation exists, but TypeScript cannot verify agreement between the producer and those positional consumers.

// Existing persisted order:
[preset, version, clef, key, policy, pool,
 activity, adaptive, input, optionalEditorIdentity]

Fix: introduce one typed encoder/decoder returning named fields. Preserve the current serialized bytes and supported 9/10-element shapes initially, so a cleanup does not reset benchmarks or detach saved observations.

Acceptance: existing backups retain identical fingerprints and benchmark matches; malformed and future contexts are still rejected.

06
LaterMeasured artifact cost

Full fonts are embedded in each app’s CSS.

The build turns both TTF files into data URLs. Together the source fonts are 848,172 bytes; each of the three app stylesheets embeds them again. A style update therefore changes a large font-bearing asset, and each independently cached app carries its own copy.

StylesheetRaw bytesLocal gzip bytes
Tuner / Tone / Tempo1,184,572488,355
tuNotes1,233,116495,444
Uno2341,194,213490,446

These are local build measurements, not observed Cloudflare transfer sizes. The former standalone-HTML delivery helped justify inlining; that delivery is now retired.

Fix: evaluate self-hosted WOFF2 assets and the glyph coverage actually needed. First allow emitted font files in the build and include them in every relevant integrity/precache manifest. Keep offline independence and font notices.

Acceptance: smaller CSS and total transfer; all music symbols, weights, and offline reopening still work. Do this after data integrity and test coverage.

07
LaterConfirmed documentation drift

The architecture guide describes an older data contract.

The architecture guide says the backup schema is “now 2”; the implementation emits schema 4. It also says Stage 2 “will add” history-dependent benchmarks even though a later section describes the implemented behavior. Readers have to reconstruct chronology inside a document presented as current architecture.

Fix: make the architecture guide describe the current contracts and move stage history to clearly dated records. Document current schema compatibility beside its owner, and link there from the overview.

Acceptance: an implementer can find the current schema, migration policy, screen ownership, and validation command without reconciling contradictory stages.

A manageable first round

01 / Data

Prevent stale writes

Choose the writer policy, add two-tab regression coverage, and verify import and deletion under contention. Keep this change separate from performance work.

02 / Verification

Repair the check registry

Classify every browser runner. Repair the UIL flow and promote current rhythm workflows into the release command.

03 / Change cost

Narrow the boundaries

Profile persistence on a school device. Extract typed context decoding and rhythm screen transitions in small, independently verifiable changes.

Tooling: use what is already here.

Node’s test runner, TypeScript, Playwright, and esbuild supplied enough evidence for this audit. The immediate tooling need is a maintained test registry and reproducible persistence measurements. Adding a framework, broad lint rules, or a generic complexity score would not address the first two findings.

Keep the written-event model, injected clocks/randomness, strict backup validation at external boundaries, and deferred worker updates. Existing legacy assessment code serves captured policy compatibility; its name alone is not a reason to remove it.
